---
title: "From paper to live"
description: "Move a strategy from paper trading to a connected exchange account with the same API calls, and plan for the differences that matter."
---

A paper account and a connected account use the same operations, the same request and response models, the same errors
and the same order rules. Going live is a change of account, not a rewrite.

Test on history with your own tools, which can use Plurex's [market data](/guides/market-data), then forward test on
paper until you trust the strategy's behaviour. By then your code has handled fills, fees, funding, errors and
reconnects through the same calls it will use live.

## What stays the same

| | Paper and live |
| --- | --- |
| Operations | Every `/hosts` query and command, both account streams and the account operations, where the live host supports them |
| Models | The same `Order`, `Fill`, `Wallet`, `MarketPosition` and `AccountTransaction` shapes |
| Errors | The same error envelope and codes, such as `InsufficientFunds`, `Rejected`, `DuplicateClientOrderId`, `OrderAlreadyClosed` and `NotSupported` |
| Order rules | The same increments, minimums and value floors, validated the same way |
| Market data | The same live venue data |

## Make the switch

<Steps>
  <Step title="Find the model host">
    Read the paper host's `modelHostId` from [List hosts](/api-reference/platform/hosts/list). That is the real host
    your paper account has been simulating.
  </Step>
  <Step title="Connect an exchange account on it">
    Create an API key at the exchange and connect it with [Connect an account](/api-reference/platform/accounts/connect)
    using `modelHostId` as `hostId`. See [Connect an exchange account](/platform/add-exchange).
  </Step>
  <Step title="Re-read the live host's capabilities and markets">
    Read the model host's `capabilities` from List hosts and its market summaries from
    [List host markets](/api-reference/platform/hosts/list-markets). They are not identical to the paper host's; the
    checklist below says where they differ.
  </Step>
  <Step title="Swap the account ID">
    Point your strategy at the new account ID. Start small, and compare live fills with what paper produced.
  </Step>
</Steps>

## Differences to plan for

Paper keeps these differences in the open: each one is visible in the hosts' capabilities and market summaries, or
listed here so you can plan for it.

### Leverage and liquidation

Paper applies [one simple model](/paper/leverage-and-liquidation) on every host, so treat its leverage results as a
guide to how a strategy behaves, not a promise of where a live position closes.

| | Paper | Live |
| --- | --- | --- |
| Position size | Maintenance margin and maximum leverage are the same at every size | Exchanges usually tighten both as a position grows, so a large position can be refused or liquidated sooner, above all in an illiquid market |
| Changing leverage | Refused while the market has a position or an open order, and reaches that market only | May be allowed with a position open, and can reach further: read `settings.leverage.setEffectScope` |
| Margin on a position | Locked at the opening price | May follow the mark |
| Unrealised gains | Never fund new orders | May count towards what is available |
| Margin modes | Cross margin only | May include others, such as isolated or portfolio margin. List margin states returns `422 NotSupported` for an account margin mode the host does not support. |
| Liquidation | Closes the largest position in full, as far as the book allows | Follows the exchange's own process, which may reduce a position in steps, or use insurance funds and auto-deleveraging |
| Losses beyond the account | Written off to zero as an `Adjustment` | Follow the exchange's rules |
| Reporting | `origin` is always set | `liquidationPrice`, `origin`, `totalMaintenanceMargin` and `maintenanceMarginUsage` can each be `null`, and a liquidation price is that host's own estimate |

Before your first live order, read the market's leverage with
[Get leverage](/api-reference/platform/hosts/get-leverage), since the exchange's current setting applies to your
orders, and set it with [Set leverage](/api-reference/platform/hosts/set-leverage) where the market allows. Read
[List margin states](/api-reference/platform/hosts/list-margin-states) before you size your first positions.

### Capabilities paper offers that the live host may not

The paper host provides some operations and options whatever its model host supports. Check the live host's
capabilities before relying on:

- the `ByClientOrderId` variants of order lookups and cancels, batch lookups, and the `Before` and `After` variants of
  [List closed orders](/api-reference/platform/hosts/list-closed-orders);
- [List fills](/api-reference/platform/hosts/list-fills) by order ID;
- [Cancel all orders](/api-reference/platform/hosts/cancel-all-orders);
- IOC and FOK on limit and trigger limit orders, and FOK on market and trigger market orders (`supportedTimeInForce`
  in each order type's options);
- [Get position mode](/api-reference/platform/hosts/get-position-mode) on perpetuals where the live host reports none;
- the order stream (`accountOrders.subscribeToAccountOrders`); without it, poll
  [List open orders](/api-reference/platform/hosts/list-orders) and [Get an order](/api-reference/platform/hosts/get-order);
- the scope of a leverage or position mode change (`setEffectScope` in the market's `settings`); live, a change may
  apply to more than one market or the whole account.

### Capabilities the live host may offer that paper does not

- Notional-sized market orders on perpetuals. Paper perpetual market orders are sized in contracts only.
- Trigger reference prices paper cannot evaluate from live data. Compare the `trigger.referencePrice` options of each
  market's trigger order types on both hosts.
- Dated futures and option markets, which paper does not list.

### Fees and funding

Live fees follow your real exchange account: its tier, volume, promotions, fee-token discounts and the exchange's own
rules for which asset a fee is charged in. Paper charges the tier you selected, and charges spot fees in the quote
asset. Live funding settles at the exchange's own price; paper uses the venue's mark price at the funding time.
See [Fees and funding](/paper/fees-and-funding).

### Execution realism

Paper adds no artificial latency: orders see the real path through Plurex and its live market data. It models your
market impact as the depth your own orders take, and estimates queue position from visible size and public trades.
Other traders can still react to a live order, so live fills will differ, most of all on passive fills and large
sweeps. Paper's market order protection is its own: the exchange may cap a market order at a different price, or not
at all.

### Funds held by trigger orders

Paper holds nothing for a trigger order while it waits, and checks funds, collateral and position only when it fires.
A trigger that cannot be accepted then ends `Rejected` on the order stream, not in the submit response. Some exchanges
reserve funds when you place a trigger order, so live, a waiting trigger may reduce your available balance, or be
refused at placement where paper accepted it.

### Reduce-only orders

Paper trims a reduce-only or `Close` order that is larger than the position left to close, counting other open orders
that would close it, and rejects one only when nothing is left. Exchanges have their own rules, and some reject where
paper trims. Size reduce-only orders from the current position on both.

### Collateral

Paper models the model host's collateral: the same kind of cross pool, its main collateral assets and their weights.
A live account can have more, such as collateral tiers and assets you switch on or off.

### Insufficient funds and collateral

Paper rejects any order that its balance or collateral cannot cover with `422 InsufficientFunds`. A live host returns
`InsufficientFunds` where it recognises the exchange's error, and may report other shortfalls as `422 Rejected`.
Handle both codes as "not enough funds or collateral".

### Transactions

Paper posts `Deposit`, `Withdrawal`, `TradingFee`, `Settlement`, `Trade`, `FundingPayment` and `Adjustment` transactions. A live host reports
its own set, which may include types such as `Transfer`, `BorrowInterest` or `LiquidationFee`, and may not report
some of paper's. Read `accountTransactions.supportedTransactionTypes`, and handle types you do not recognise.

A paper host always offers the transaction stream. A live host may not: check
`accountTransactions.subscribeToAccountTransactions`, and fall back to polling List transactions where there is no
stream.

## Write strategies that adapt

Never hard-code a host. Read the host's capabilities and the market's order rules when the strategy starts, and choose
behaviour from them, so the same code runs on paper and live.

```python
import os

import requests

BASE = "https://api.plurex.io/api/v1"
HEADERS = {
    "X-API-KEY": os.environ["PLUREX_API_KEY"],
    "X-API-SECRET": os.environ["PLUREX_API_SECRET"],
}


def query(path, body):
    response = requests.request("QUERY", f"{BASE}/{path}", json=body, headers=HEADERS)
    response.raise_for_status()
    return response.json()


def supported(support):
    # Host-wide entries are Supported or NotSupported; market-level entries
    # (PerMarket) also need the market summary's own flag.
    return support["type"] == "Supported"


def load_profile(host_id, instrument):
    hosts = query("hosts/query/List", {})["items"]  # follow nextCursor in production
    host = next(h for h in hosts if h["id"] == host_id)
    markets = query("hosts/query/ListMarkets", {
        "hostId": host_id,
        "base": instrument["base"],
        "quote": instrument["quote"],
        "types": [instrument["type"]],
    })["items"]
    market = next(m for m in markets if m["instrument"] == instrument)
    caps = host["capabilities"]
    market_order = market["orderTypes"]["market"]
    trigger = market["orderTypes"]["triggerMarket"]

    return {
        "is_paper": host["isPaper"],
        "rules": market["orderTypes"]["limit"],
        # Size or Notional, whichever this market accepts for buys
        "market_buy_sizing": market_order["sizingSupport"]["buy"] if market_order else [],
        # Correlate orders by clientOrderId only where the host supports it
        "use_client_order_id": supported(caps["orders"]["submitOrder"]["clientOrderId"]),
        # Set leverage only where the market has a settable leverage
        "can_set_leverage": bool(market["settings"]["leverage"]
                                 and market["settings"]["leverage"]["setEffectScope"]),
        # Stream order changes where supported; otherwise poll open orders
        "stream_orders": supported(caps["accountOrders"]["subscribeToAccountOrders"]),
        # Stream transactions where supported; otherwise poll ListTransactions
        "stream_transactions": supported(caps["accountTransactions"]["subscribeToAccountTransactions"]),
        # Stops: pick a reference price the market offers, rather than assuming one
        "stop_reference": choose_reference(trigger["trigger"]["referencePrice"]) if trigger else None,
    }


def choose_reference(policy, preferred=("Mark", "LastTrade", "Index")):
    if policy["type"] == "HostSelected":
        return None  # omit trigger.reference; the host uses policy["price"]
    return next((p for p in preferred if p in policy["prices"]), policy["prices"][0])
```

Read executions with [List fills](/api-reference/platform/hosts/list-fills) on both: the order stream reports that an
order filled, not each execution's details.

Run `load_profile` for the paper host while you forward test and for the model host when you go live. If a decision
your strategy depends on comes out differently, you find out at start-up rather than from a rejected order.

<Tip>
  Before going live, diff the two profiles. Anything that changed, such as sizing modes, reference prices or leverage,
  is a code path your strategy has not exercised on paper.
</Tip>
