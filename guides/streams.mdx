A stream follows one topic, such as one account's orders or one market's order book, and pushes each change as it happens, so you do not have to poll. You open it with an ordinary `POST`, and the response stays open, carrying one JSON message per line. Streams work the same way for real and paper accounts.

| Stream | Topic | First line |
| --- | --- | --- |
| [Account orders](/api-reference/platform/hosts/subscribe-to-account-orders) | One account | The first change. No snapshot: read [List open orders](/api-reference/platform/hosts/list-orders) |
| [Account transactions](/api-reference/platform/hosts/subscribe-to-account-transactions) | One account | The first posting. No snapshot: read [List account transactions](/api-reference/platform/hosts/list-transactions) |
| [Order book](/api-reference/platform/venues/subscribe-to-order-books) | One market | `Reset` with the whole book |
| [Public trades](/api-reference/platform/venues/subscribe-to-trades) | One market | `Reset` with the recent trades |
| [Prices](/api-reference/platform/venues/subscribe-to-prices) | One market and price kind | `Reset` with the current price |
| [Best bid and ask](/api-reference/platform/venues/subscribe-to-best-quotes) | One market | `Reset` with the current quote |
| [Market statistics](/api-reference/platform/venues/subscribe-to-market-statistics) | One market | `Reset` with the current statistics |
| [Indicative funding](/api-reference/platform/venues/subscribe-to-indicative-fundings) | One perpetual | `Reset` with the current estimate |
| [Open interest](/api-reference/platform/venues/subscribe-to-open-interests) | One derivative | `Reset` with the current amount |
| [Candles](/api-reference/platform/venues/subscribe-to-candles) | One market, price kind and interval | `Reset` with the recent candles |

## Check support first

A stream that the host, venue or market does not offer fails before it starts, with `422 NotSupported`. Each stream page's **Check support** block names the capability to read:

- Account streams: the host's `accountOrders.subscribeToAccountOrders` and `accountTransactions.subscribeToAccountTransactions`, from [List hosts](/api-reference/platform/hosts/list). `accountOrders.changes` and `accountOrders.includesFillDetails` say what the order stream sends.
- Market data streams: the venue's `subscribeTo…` capabilities, from [List venues](/api-reference/platform/venues/list). Where an entry is `PerMarket`, the market's `marketData` from [List venue markets](/api-reference/platform/venues/list-markets) says whether that market streams it, for example `marketData.prices.mark.subscribe`.

See [Host capabilities](/capabilities/host-capabilities) and [Venue capabilities](/capabilities/venue-capabilities).

## Open a stream

Send the topic as the JSON body, with the same `X-API-KEY` and `X-API-SECRET` headers as every other operation. With `curl`, `--no-buffer` prints each line as it arrives:

```bash
curl --no-buffer --request POST \
  --url https://api.plurex.io/api/v1/venues/stream/SubscribeToOrderBooks \
  --header 'Content-Type: application/json' \
  --header "X-API-KEY: $PLUREX_API_KEY" \
  --header "X-API-SECRET: $PLUREX_API_SECRET" \
  --data '{
    "venueId": "bybit",
    "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" }
  }'
```

Find venue IDs and instruments with [List venues](/api-reference/platform/venues/list) and [List venue markets](/api-reference/platform/venues/list-markets). An account stream takes `{"accountId": "…"}`.

Everything that can go wrong before the stream starts is an ordinary error response with the [error envelope](/api-reference/platform/errors): `401 Unauthenticated`, `400 InvalidRequest`, `404` for an unknown venue or account, `403 Forbidden` for an account you cannot access, `422 NotSupported` for an unsupported stream or market. Fix the request rather than retrying it in a loop; only `429` and `5xx` are worth retrying.

A `200` means the subscription is live. The response is `application/jsonl` and stays open: one JSON message per line, until the last line, which is always `Ended`. Close the response to stop the stream.

## Read the lines

Read the body line by line as it arrives. Every message has a `type`:

| `type` | Streams | Meaning |
| --- | --- | --- |
| `Event` | Account streams | One change: an order change, or a new balance posting. |
| `Reset` | Market data streams | The topic's whole current state. Replace everything you hold for this stream. |
| `Update` | Market data streams | A change to apply on top of the last `Reset`. |
| `Ended` | All | The stream stopped. Nothing more follows. |

`Event`, `Reset` and `Update` carry `timestamp`, when Plurex sent the message, and `data`, the payload. Its shape is on each stream's page.

A **blank line** is a keepalive. One arrives as the stream opens, and again at least every 15 seconds while the stream is quiet. Skip it, but treat a stream that stays silent much longer than that as lost.

New message types and fields can be added. Ignore a `type` you do not recognise.

## Market data streams

A market data stream starts with a `Reset` holding the topic's current state, then sends `Update`s. A `Reset` can arrive again at any time and replaces everything you hold: do not merge it with your copy.

```json
{"type":"Reset","timestamp":"2026-10-27T09:00:00.120Z","data":{"bids":[{"price":"67250.1","size":"0.42"}],"asks":[{"price":"67250.2","size":"0.08"}],"observedAt":"2026-10-27T09:00:00.101Z","receivedAt":"2026-10-27T09:00:00.115Z"}}

{"type":"Update","timestamp":"2026-10-27T09:00:00.320Z","data":{"bids":[{"price":"67250.1","size":"0.9"}],"asks":[{"price":"67250.2","size":"0"}],"observedAt":"2026-10-27T09:00:00.301Z","receivedAt":"2026-10-27T09:00:00.316Z"}}
```

How to apply an `Update` depends on the stream:

| Stream | `Reset` | `Update` |
| --- | --- | --- |
| Order book | The whole book, best price first. | Only the levels that changed, each with its new total size. Set each level; size `"0"` removes it. Levels not listed are unchanged. |
| Public trades | The recent trades. They can repeat trades an `Update` already delivered, so replace your trade history and do not add them to running totals. | New trades. |
| Prices, best bid and ask, statistics, indicative funding, open interest | The current value. | The complete new value. Replace the old one; a field that is now `null` was cleared. |
| Candles | The recent candles, oldest first, ending with the current one, still forming. Read older candles with [List candles](/api-reference/platform/venues/list-candles). | The current candle alone. The same `startAt` replaces the current candle; a later `startAt` completes it and starts the next. |

Values carry `observedAt`, the venue's time when it reports one, and `receivedAt`, when Plurex received it. See [Read market data](/guides/market-data) for what each value means.

## Account streams

An account stream sends an `Event` per change and **no snapshot**. It does not replay changes from before it opened, so pair it with a read of the current state, as in [Keep a correct local copy](#keep-a-correct-local-copy).

### Order events

Each order event carries the `change` that happened and the complete `order`, exactly as [Get an order](/api-reference/platform/hosts/get-order) returns it:

```json
{
  "type": "Event",
  "timestamp": "2026-10-26T08:17:18.732Z",
  "data": {
    "change": { "type": "Cancelled" },
    "order": {
      "type": "Limit",
      "id": "BTC-USDT-SPOT|5fee96c0-8063-412d-8b4d-e36e44a8ea2d",
      "createdAt": "2026-10-26T08:17:17.709Z",
      "side": "Buy",
      "instrument": { "type": "Spot", "base": "BTC", "quote": "USDT" },
      "state": "Cancelled",
      "sizeTraded": "0",
      "averagePrice": null,
      "realizedPnl": null,
      "totalFees": [],
      "clientOrderId": "my-order-1",
      "size": "1",
      "price": "90"
    }
  }
}
```

| `change.type` | Meaning |
| --- | --- |
| `Created` | The host has the order. |
| `FillApplied` | The traded size increased. The order carries the cumulative `sizeTraded`, `averagePrice` and `state`. `fill` is the execution, or `null` when the host reports only the cumulative order state (`includesFillDetails` is `false`); read executions with [List fills](/api-reference/platform/hosts/list-fills). |
| `Cancelled` | The order was cancelled. |
| `Rejected` | The host rejected the order. `reason` and `code` are the host's own text and code, or `null`. The `code` is the host's native code, not a Plurex error code. |
| `Unknown` | A host change with no standard meaning. `nativeType` holds the host's own event type. |

Because every event carries the whole order, you do not need to rebuild state from the change. Store the latest order you receive for each order ID and use `change` to decide what to react to. New change types can be added, so handle an unrecognised `type` the same way as `Unknown`.

### Transaction events

Each transaction event is one new balance posting, with the same `id` that [List account transactions](/api-reference/platform/hosts/list-transactions) returns for it:

```json
{
  "type": "Event",
  "timestamp": "2026-10-26T08:20:00.120Z",
  "data": {
    "id": "trade-fee:7f3a",
    "effectiveAt": "2026-10-26T08:20:00.104Z",
    "amount": { "asset": "USDT", "value": "-0.055" },
    "type": "TradingFee",
    "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
    "orderId": "BTC-USDT-PERP|0b6c1e52-2f7e-4c55-9d43-1c1a9b6f2e10",
    "fillId": "fill-91",
    "positionId": null,
    "groupId": "trade:BTC-USDT-PERP:fill-91",
    "nativeType": "TRADE_FEE",
    "description": null
  }
}
```

`amount` is signed from your side: positive increases the balance, negative decreases it. Transaction events are not ordered relative to order events, so a fee can arrive before or after the fill it belongs to. See [Balances, positions and settings](/guides/portfolio#transactions) for posting types and links.

### Keep a correct local copy

<Steps>
  <Step title="Open the stream first">
    Wait for the `200`. From then on every change arrives as an event; keep reading and queue the events while you do the next step.
  </Step>
  <Step title="Read the current state">
    Page through [List open orders](/api-reference/platform/hosts/list-orders) (or recent [transactions](/api-reference/platform/hosts/list-transactions)) until `nextCursor` is `null`. This is your starting copy.
  </Step>
  <Step title="Apply events on top">
    Apply the queued events, then live ones, in the order they arrive. For orders, the newest event for an order ID replaces what you hold; drop an order from your open set once its state is `Filled`, `Cancelled` or `Rejected`. For transactions, add any posting whose `id` you do not have.
  </Step>
  <Step title="When the stream stops, do both again">
    Changes made while no stream was open are gone from the stream. Open it again, then read the state again and replace your copy.
  </Step>
</Steps>

Opening the stream before you read is what closes the gap: anything that changes after your read also arrives as an event, and because each event carries the complete order, applying an event on top of slightly newer data still ends on the latest state.

For transactions, re-read history a little further back than the newest posting you hold, so a posting that reached the host's history late is not missed. The `listTransactions` capability's `defaultOrdering` says whether history comes newest or oldest first.

## When a stream stops

A stream stops in one of two ways.

**With `Ended`.** The last line says why, with a `code` from the [error catalogue](/api-reference/platform/errors), for example `UpstreamFailure` when the venue's or host's own feed ended. `message` is for logs; do not parse it.

```json
{"type":"Ended","code":"UpstreamFailure","message":"Upstream stream ended"}
```

**Without `Ended`.** The response ends or fails without an `Ended` line, the connection drops, or the stream falls too far behind (see below). Messages have been lost.

Either way, open the stream again after a short, randomised delay, so that many clients do not reconnect at once, and rebuild from its first message: the new `Reset` for market data, or a fresh read of the current state for an account stream. Back off further if reopening keeps failing, and stop on a `4xx` other than `429`: that needs a fix, not a retry.

## Keep up with the stream

Read lines as they arrive. A stream whose client falls too far behind is cut, without an `Ended` line, rather than delaying it. Hand messages to a queue as soon as you read them, and do slow work, such as REST reads, elsewhere.

Open one stream per topic. Each stream is cut on its own, so a busy order book never delays your order events. Streams work over HTTP/1.1, which holds a connection per stream, and HTTP/2, which shares one connection between all your streams.

## A resilient reader

This sketch keeps a local order book for one market and the set of open orders for one account, across `Ended`, disconnects and resets. It uses [`requests`](https://requests.readthedocs.io/). Each stream runs in its own thread, so a slow REST read never holds a stream back.

```python
import json, os, queue, random, threading, time
import requests

API = "https://api.plurex.io/api/v1"
HEADERS = {
    "X-API-KEY": os.environ["PLUREX_API_KEY"],
    "X-API-SECRET": os.environ["PLUREX_API_SECRET"],
}
RETRYABLE = {429, 500, 502, 503, 504}
TERMINAL = {"Filled", "Cancelled", "Rejected"}


def follow(path, body, on_open, on_message):
    """Keep one stream open. Calls on_open() after each 200, then on_message() for every line."""
    delay = 1
    while True:
        try:
            # The read timeout is the longest silence allowed; a keepalive arrives at least every 15 s.
            with requests.post(f"{API}/{path}", json=body, headers=HEADERS,
                               stream=True, timeout=(10, 45)) as response:
                if response.status_code != 200:
                    error = response.json()
                    if response.status_code not in RETRYABLE:
                        raise RuntimeError(f"{response.status_code} {error['code']}: {error['message']}")
                else:
                    on_open()
                    delay = 1
                    for line in response.iter_lines():
                        if not line:
                            continue                     # keepalive
                        message = json.loads(line)
                        if message["type"] == "Ended":
                            print("stream ended:", message["code"], message["message"])
                            break
                        on_message(message)
                    # Ended, or the body finished without it: either way, reopen.
        except (requests.ConnectionError, requests.Timeout, requests.exceptions.ChunkedEncodingError):
            pass                                         # lost: reopen
        time.sleep(delay * random.uniform(0.5, 1.5))     # randomised, so clients do not reconnect together
        delay = min(delay * 2, 60)


# Market data: a Reset replaces the book, an Update sets or removes levels.
book = {"bids": {}, "asks": {}}

def on_book(message):
    if message["type"] == "Reset":
        for side in ("bids", "asks"):
            book[side] = {}
    if message["type"] in ("Reset", "Update"):
        for side in ("bids", "asks"):
            for level in message["data"][side]:
                if level["size"] == "0":
                    book[side].pop(level["price"], None)
                else:
                    book[side][level["price"]] = level["size"]


# Account orders: open the stream, read the current state, then apply events on top.
ACCOUNT_ID = os.environ["PLUREX_ACCOUNT_ID"]
open_orders = {}
events = queue.Queue()

def read_open_orders():
    orders, cursor = {}, None
    while True:
        body = {"accountId": ACCOUNT_ID, "query": {"type": "Global"}}
        if cursor:
            body["cursor"] = cursor
        response = requests.post(f"{API}/hosts/query/ListOpenOrders", json=body, headers=HEADERS, timeout=10)
        response.raise_for_status()
        page = response.json()
        for order in page["items"]:
            orders[order["id"]] = order
        cursor = page["nextCursor"]
        if cursor is None:
            return orders

def apply(order):
    if order["state"] in TERMINAL:
        open_orders.pop(order["id"], None)
    else:
        open_orders[order["id"]] = order                 # newest event wins

def reconcile():
    while True:
        item = events.get()
        if item == "opened":                             # a new stream: rebuild from the current state
            open_orders.clear()
            open_orders.update(read_open_orders())
        elif item["type"] == "Event":
            apply(item["data"]["order"])                 # events queued during the read apply after it


threading.Thread(target=reconcile, daemon=True).start()
threading.Thread(target=follow, daemon=True, args=(
    "hosts/stream/SubscribeToAccountOrders", {"accountId": ACCOUNT_ID},
    lambda: events.put("opened"), events.put)).start()
follow("venues/stream/SubscribeToOrderBooks",
       {"venueId": "bybit", "instrument": {"type": "Perp", "base": "BTC", "quote": "USDT"}},
       lambda: None, on_book)
```

The order stream's thread only queues what it reads, so it keeps up while `reconcile` pages through open orders. The order book needs nothing on open: its first line is a `Reset`.

## What a stream does not promise

- No snapshot on an account stream, and no replay of missed changes on any stream.
- No sequence numbers or resume tokens. A gap shows as a fresh `Reset`, an `Ended`, or a stream that stops without one.
- No ordering between streams, such as between the order stream and the transaction stream.
- No individual executions when `includesFillDetails` is `false`.
