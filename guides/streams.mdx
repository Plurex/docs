---
title: "Stream account updates"
description: "Follow your accounts' orders and balance postings over WebSocket, and keep a correct local copy through disconnects."
---

Two WebSocket streams push your accounts' activity as it happens, so you do not have to poll. Both work the same way for real and paper accounts.

| Stream | Address | Reconcile with |
| --- | --- | --- |
| [Account orders](/api-reference/platform/hosts/subscribe-to-account-orders) | `wss://api.plurex.io/api/v1/hosts/stream/SubscribeToAccountOrders` | [List open orders](/api-reference/platform/hosts/list-orders) |
| [Account transactions](/api-reference/platform/hosts/subscribe-to-account-transactions) | `wss://api.plurex.io/api/v1/hosts/stream/SubscribeToAccountTransactions` | [List account transactions](/api-reference/platform/hosts/list-transactions) |

One connection carries one stream type for many accounts. You connect once, then subscribe and unsubscribe accounts with messages, without reconnecting. Each account on a connection is a **topic**, and every message names the topic it belongs to.

A stream sends only what happens after an account is subscribed. It has no snapshot and does not replay events you missed, so a correct client always pairs it with a REST read. The [reconciliation pattern](#keep-a-correct-local-copy) below shows how.

## Check the host first

Read the account's host from [List hosts](/api-reference/platform/hosts/list) and check its capabilities before you subscribe. An account whose host does not support the stream is refused with `NotSupported`.

| Capability | What it tells you |
| --- | --- |
| `accountOrders.subscribeToAccountOrders` | Whether the order stream exists on this host. |
| `accountOrders.changes` | Which change types the host sends: `Created`, `FillApplied`, `Cancelled`, `Rejected`. A host may send fewer. |
| `accountOrders.includesFillDetails` | Whether `FillApplied` events carry the individual execution. When `false`, `fill` is `null`; read executions with [List fills](/api-reference/platform/hosts/list-fills). |
| `accountTransactions.subscribeToAccountTransactions` | Whether the transaction stream exists on this host. |
| `accountTransactions.supportedTransactionTypes` | Which posting types the host reports. |

See [Host capabilities](/capabilities/host-capabilities) for how to read these entries.

## Connect and subscribe

Send the same `X-API-KEY` and `X-API-SECRET` headers you use for HTTP on the upgrade request. If authentication fails, you get an ordinary HTTP error response with the [error envelope](/api-reference/platform/errors), before any WebSocket is opened. Fix the credentials rather than reconnecting in a loop.

Once connected, send a `Subscribe` message with your own request `id` and the accounts to stream:

```json
{
  "type": "Subscribe",
  "id": "sub-1",
  "topics": [{ "accountId": "acc_123" }, { "accountId": "acc_456" }]
}
```

The server answers each `Subscribe` in two parts:

1. A `Rejected` for each account it refuses, with the same `code` an HTTP request for that account would get: for example `AccountNotFound`, `Forbidden`, or `NotSupported` when the host does not offer the stream.
2. One `Subscribed` listing the accounts now streaming. Their events follow it.

```json
{ "type": "Rejected", "id": "sub-1", "topic": { "accountId": "acc_456" }, "code": "Forbidden", "message": "Access denied" }
```

```json
{ "type": "Subscribed", "id": "sub-1", "topics": [{ "accountId": "acc_123" }] }
```

A refused account never closes the connection; the other accounts stream normally. Subscribing an account that is already streaming lists it again in `Subscribed` without opening a second stream for it.

To stop streaming an account, send `Unsubscribe`. The reply is one `Unsubscribed`, after which nothing more arrives for those accounts. Accounts that were not streaming are acknowledged too.

```json
{ "type": "Unsubscribe", "id": "unsub-1", "topics": [{ "accountId": "acc_123" }] }
```

```json
{ "type": "Unsubscribed", "id": "unsub-1", "topics": [{ "accountId": "acc_123" }] }
```

The request `id` is 1 to 64 characters and is echoed on its replies, so you can match them to your requests.

With [websocat](https://github.com/vi/websocat), connect and then type the `Subscribe` message as one line:

```bash
websocat \
  --header "X-API-KEY: $PLUREX_API_KEY" \
  --header "X-API-SECRET: $PLUREX_API_SECRET" \
  "wss://api.plurex.io/api/v1/hosts/stream/SubscribeToAccountOrders"
```

With the Python [`websockets`](https://websockets.readthedocs.io/) library, version 14 or later:

```python
import asyncio, json, os
from websockets.asyncio.client import connect

HEADERS = {
    "X-API-KEY": os.environ["PLUREX_API_KEY"],
    "X-API-SECRET": os.environ["PLUREX_API_SECRET"],
}
URL = "wss://api.plurex.io/api/v1/hosts/stream/SubscribeToAccountOrders"

async def main():
    async with connect(URL, additional_headers=HEADERS) as ws:
        await ws.send(json.dumps({
            "type": "Subscribe",
            "id": "sub-1",
            "topics": [{"accountId": os.environ["PLUREX_ACCOUNT_ID"]}],
        }))
        async for raw in ws:
            message = json.loads(raw)
            if message["type"] == "Event":
                data = message["data"]
                print(message["topic"]["accountId"], data["change"]["type"], data["order"]["state"])
            else:
                print(message)

asyncio.run(main())
```

WebSocket ping and pong frames keep the connection alive; most client libraries answer pings for you.

<Warning>
  Browser authentication is not supported. Browsers cannot set custom headers on a WebSocket upgrade, so connect from a server or a native client.
</Warning>

### Limits

- A connection streams at most 25 accounts at a time. Accounts beyond the limit are refused with `Rejected` and code `InvalidRequest`. Open another connection for more.
- A connection with no accounts streaming for 30 seconds is closed with code `1008` and reason `No topics`. This includes the time right after you connect, and refused accounts do not count, so subscribe promptly after connecting.
- Send only `Subscribe` and `Unsubscribe` messages. A message the server cannot decode closes the connection with code `1008`.

## Messages

Every message is one JSON text frame with a `type`. The server sends:

| `type` | When | Fields |
| --- | --- | --- |
| `Subscribed` | Reply to `Subscribe` | `id`, `topics` now streaming |
| `Rejected` | Before `Subscribed`, once per refused account | `id`, `topic`, `code`, `message` |
| `Unsubscribed` | Reply to `Unsubscribe` | `id`, `topics` no longer streaming |
| `Event` | An order change or a posting on a streaming account | `topic`, `timestamp`, `data` |
| `Ended` | A streaming account stopped streaming | `topic`, `code`, `message` |

New message types can be added, so ignore a `type` you do not recognise. Order holds per account, not across accounts: two events for the same account arrive in the order they happened, while events for different accounts can interleave in any order.

In an `Event`, `timestamp` is when Plurex sent the event, and `data` is the payload.

### Order events

Each order event carries the `change` that happened and the complete `order`, exactly as [Get an order](/api-reference/platform/hosts/get-order) returns it:

```json
{
  "type": "Event",
  "topic": { "accountId": "acc_123" },
  "timestamp": "2026-10-25T09:31:12.408Z",
  "data": {
    "change": {
      "type": "FillApplied",
      "fill": {
        "orderId": "ord_789",
        "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
        "side": "Buy",
        "executedAt": "2026-10-25T09:31:12.391Z",
        "price": "60000.0",
        "size": "0.004",
        "fees": [{ "asset": "USDT", "value": "0.048" }],
        "realizedPnl": null,
        "id": "exec_5521",
        "role": "Maker"
      }
    },
    "order": {
      "type": "Limit",
      "id": "ord_789",
      "createdAt": "2026-10-25T09:30:00Z",
      "side": "Buy",
      "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
      "state": "Live",
      "sizeTraded": "0.004",
      "averagePrice": "60000.0",
      "realizedPnl": null,
      "totalFees": [{ "asset": "USDT", "value": "0.048" }],
      "clientOrderId": "grid-buy-0042",
      "size": "0.010",
      "price": "60000.0"
    }
  }
}
```

| `change.type` | Meaning |
| --- | --- |
| `Created` | The host has the order. |
| `FillApplied` | The traded size increased. The order carries the cumulative `sizeTraded`, `averagePrice` and `state`. `fill` is the execution, or `null` when the host reports only the cumulative order state. |
| `Cancelled` | The order was cancelled. |
| `Rejected` | The host rejected the order. `reason` and `code` are the host's own text and code, or `null`. The `code` is the host's native code, not a Plurex error code. |
| `Unknown` | A host change with no standard meaning. `nativeType` holds the host's own event type. |

```json
{
  "type": "Event",
  "topic": { "accountId": "acc_123" },
  "timestamp": "2026-10-25T09:32:40.020Z",
  "data": {
    "change": { "type": "Rejected", "reason": "Insufficient margin", "code": "MARGIN_LOW" },
    "order": {
      "type": "Market",
      "id": "ord_812",
      "createdAt": "2026-10-25T09:32:39.950Z",
      "side": "Buy",
      "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
      "state": "Rejected",
      "sizeTraded": "0",
      "averagePrice": null,
      "realizedPnl": null,
      "totalFees": [],
      "clientOrderId": null,
      "sizing": { "type": "Size", "size": "5.000" }
    }
  }
}
```

Because every event carries the whole order, you do not need to rebuild state from the change. Store the latest order you receive for each order ID and use `change` to decide what to react to. New change types can be added, so handle an unrecognised `type` the same way as `Unknown`.

### Transaction events

Each transaction event is one balance posting, with the same `id` that [List account transactions](/api-reference/platform/hosts/list-transactions) returns for it:

```json
{
  "type": "Event",
  "topic": { "accountId": "acc_123" },
  "timestamp": "2026-10-25T09:31:12.512Z",
  "data": {
    "id": "txn_40213",
    "effectiveAt": "2026-10-25T09:31:12.391Z",
    "amount": { "asset": "USDT", "value": "-0.048" },
    "type": "TradingFee",
    "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
    "orderId": "ord_789",
    "fillId": "exec_5521",
    "positionId": null,
    "groupId": null,
    "nativeType": "TRADE",
    "description": null
  }
}
```

`amount` is signed from your side: positive increases the balance, negative decreases it. Transaction events are ordered among themselves but not relative to order events, so a fee can arrive before or after the fill it belongs to. See [Balances, positions and settings](/guides/portfolio#transactions) for posting types and links.

### Ended

`Ended` means one account stopped streaming, for example because the host's own feed ended (`UpstreamFailure`). Nothing more arrives for that account, and the connection stays open for the others:

```json
{ "type": "Ended", "topic": { "accountId": "acc_123" }, "code": "UpstreamFailure", "message": "Upstream stream ended" }
```

Subscribe the account again, then read its REST state again, as after a disconnect.

## Keep a correct local copy

The streams promise no snapshot, no replay, no sequence numbers and no resume point. The pattern that stays correct anyway, per account:

<Steps>
  <Step title="Subscribe first">
    Connect, send `Subscribe`, and wait for `Subscribed` to list the account. Events for it follow from there; keep reading them while you do the next step.
  </Step>
  <Step title="Read the current state">
    Page through [List open orders](/api-reference/platform/hosts/list-orders) (or recent [transactions](/api-reference/platform/hosts/list-transactions)) until `nextCursor` is `null`. This is your starting copy.
  </Step>
  <Step title="Apply events on top">
    Apply the events that arrived during the read, then live ones, in the order they arrive. For orders the newest event for an order ID replaces what you hold; drop an order from your open set once its state is `Filled`, `Cancelled` or `Rejected`. For transactions, add any posting whose `id` you do not have.
  </Step>
  <Step title="After Ended or any disconnect, do both again">
    Events sent while an account was not streaming are gone. Subscribe again (after reconnecting, if the connection closed), then read the REST state again and replace your copy.
  </Step>
</Steps>

Subscribing before you read is what closes the gap: anything that changes after your REST read also arrives as an event, and because each event carries the complete order, applying an event on top of slightly newer REST data still ends on the latest state.

### Keep up with the stream

Read messages as they arrive. A connection that falls too far behind is closed with code `1013` and reason `Slow consumer`, rather than delaying the stream for everyone. Do slow work, such as REST reads, without pausing the socket: hand messages to a queue as soon as they arrive. Streaming fewer accounts per connection also reduces the load on each.

This sketch keeps the set of open orders correct for several accounts across `Ended` and reconnects. It uses `websockets` 14 or later and `httpx`. A reader task drains the socket into a queue, so the REST reads never hold it back:

```python
import asyncio, json, os, uuid
import httpx
from websockets.asyncio.client import connect
from websockets.exceptions import ConnectionClosed, InvalidHandshake, InvalidStatus

API = "https://api.plurex.io/api/v1"
STREAM = "wss://api.plurex.io/api/v1/hosts/stream/SubscribeToAccountOrders"
ACCOUNTS = [os.environ["PLUREX_ACCOUNT_ID"]]   # up to 25 per connection
HEADERS = {
    "X-API-KEY": os.environ["PLUREX_API_KEY"],
    "X-API-SECRET": os.environ["PLUREX_API_SECRET"],
}
TERMINAL = {"Filled", "Cancelled", "Rejected"}

async def read_open_orders(http, account_id):
    orders, cursor = {}, None
    while True:
        body = {"accountId": account_id, "query": {"type": "Global"}}
        if cursor:
            body["cursor"] = cursor
        response = await http.post(f"{API}/hosts/query/ListOpenOrders", json=body, headers=HEADERS)
        response.raise_for_status()
        page = response.json()
        for order in page["items"]:
            orders[order["id"]] = order
        cursor = page["nextCursor"]
        if cursor is None:
            return orders

def apply(orders, order):
    if order["state"] in TERMINAL:
        orders.pop(order["id"], None)
    else:
        orders[order["id"]] = order            # newest event wins

async def subscribe(ws, account_ids, delay=0):
    await asyncio.sleep(delay)
    try:
        await ws.send(json.dumps({
            "type": "Subscribe",
            "id": str(uuid.uuid4()),
            "topics": [{"accountId": account_id} for account_id in account_ids],
        }))
    except ConnectionClosed:
        pass                                   # the main loop reconnects

async def drain(ws, queue):
    try:
        async for raw in ws:
            queue.put_nowait(json.loads(raw))
        queue.put_nowait(None)                 # normal close
    except ConnectionClosed as closed:
        queue.put_nowait(closed)

async def follow_orders():
    delay = 1
    async with httpx.AsyncClient(timeout=10) as http:
        while True:
            try:
                async with connect(STREAM, additional_headers=HEADERS) as ws:
                    queue = asyncio.Queue()
                    reader = asyncio.create_task(drain(ws, queue))   # keep reading
                    try:
                        await subscribe(ws, ACCOUNTS)                # 1. subscribe
                        open_orders = {}                             # accountId -> {orderId: order}
                        while (message := await queue.get()) is not None:
                            if isinstance(message, Exception):
                                raise message
                            kind = message.get("type")
                            if kind == "Subscribed":                 # 2. read state
                                for topic in message["topics"]:
                                    account_id = topic["accountId"]
                                    open_orders[account_id] = await read_open_orders(http, account_id)
                                delay = 1
                            elif kind == "Event":                    # 3. apply events
                                apply(open_orders[message["topic"]["accountId"]], message["data"]["order"])
                            elif kind == "Ended":                    # 4. subscribe again, then re-read
                                account_id = message["topic"]["accountId"]
                                open_orders.pop(account_id, None)
                                asyncio.create_task(subscribe(ws, [account_id], delay=5))
                            elif kind == "Rejected":                 # refused: fix, do not loop
                                raise RuntimeError(f"{message['topic']['accountId']}: {message['code']} {message['message']}")
                    finally:
                        reader.cancel()
            except InvalidStatus as error:
                if error.response.status_code != 429 and error.response.status_code < 500:
                    raise          # credentials: fix, do not loop
            except httpx.HTTPStatusError as error:
                if error.response.status_code in (400, 401, 403, 404, 422):
                    raise          # the REST read itself is wrong: fix, do not loop
            except (ConnectionClosed, InvalidHandshake, OSError, httpx.HTTPError):
                pass               # 5. reconnect, subscribe and read state again
            await asyncio.sleep(delay)
            delay = min(delay * 2, 60)

asyncio.run(follow_orders())
```

Events that arrive while the sketch reads an account's REST state wait in the queue behind `Subscribed`, so they are applied after it, in order. The loop backs off on network failures, closes, and `429` and `5xx` responses, and stops on errors that need a fix.

For transactions, the same loop works on the transaction stream with `ListTransactions` in place of `ListOpenOrders`. Keep posting IDs you have seen, and after subscribing again re-read history a little further back than the newest posting you hold, so a posting that reached the host's history late is not missed. The `listTransactions` capability's `defaultOrdering` says whether history comes newest or oldest first.

## Close codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `1000` | Normal shutdown. | Reconnect if you still need updates, subscribe, then read the REST state again. |
| `1008` with reason `No topics` | No account was streaming for 30 seconds. | Subscribe promptly after connecting, and keep at least one account streaming or close the connection yourself. |
| `1008`, any other reason | The server could not decode a message you sent. | Fix the message; send only `Subscribe` and `Unsubscribe`. |
| `1011` with reason `Stream failed` | The stream itself failed. | Reconnect with a backoff, subscribe, then read the REST state again. |
| `1013` with reason `Slow consumer` | Your client fell too far behind. | Reconnect, subscribe, then reconcile. Read messages as they arrive, and stream fewer accounts per connection. |

Any other disconnect, such as a network failure, is handled the same way: reconnect, subscribe, then reconcile.

## What a stream does not promise

- No snapshot on subscribe, and no replay of missed events.
- No sequence numbers or resume tokens. A gap is detected only by `Ended` or a disconnect.
- No ordering between accounts, or between the order stream and the transaction stream.
- No individual executions when `includesFillDetails` is `false`.
- No browser authentication.
