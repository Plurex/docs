title: "Streams"
description: "Follow your accounts' orders and balance postings, and a market's order book, trades, prices and candles, as they happen, and keep a correct local copy through reconnects."
---

A stream follows one topic, such as one account's orders or one market's order book, and pushes each change as it happens, so you do not have to poll. You open it with a `QUERY` request, and the response stays open, carrying one JSON message per line. Streams work the same way for real and paper accounts.

| Stream | Topic | First line |
| --- | --- | --- |
| [Account orders](/api-reference/platform/hosts/subscribe-to-account-orders) | One account | `Reset` with the open orders |
| [Account transactions](/api-reference/platform/hosts/subscribe-to-account-transactions) | One account | The first posting. No snapshot: read [List account transactions](/api-reference/platform/hosts/list-transactions) |
| [Market data streams](/guides/market-data#follow-market-data-live) | One market, and a price kind or interval where it applies | `Reset` with the current state |

## Check support first

A stream that the host, venue or market does not offer returns `422 NotSupported` before it starts. Each stream page's **Check support** block names the capability to read: see [Host capabilities](/capabilities/host-capabilities) for account streams and [Venue capabilities](/capabilities/venue-capabilities) for market data streams.

## Open a stream

Send the topic as the JSON body. With `curl`, `--no-buffer` prints each line as it arrives:

```bash
curl --no-buffer --request QUERY \
  --url https://api.plurex.io/api/v1/venues/stream/SubscribeToOrderBookL2s \
  --header 'Content-Type: application/json' \
  --header "X-API-KEY: $PLUREX_API_KEY" \
  --header "X-API-SECRET: $PLUREX_API_SECRET" \
  --data '{
    "venueId": "bybit",
    "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" }
  }'
```

Find venue IDs and instruments with [List venues](/api-reference/platform/venues/list) and [List venue markets](/api-reference/platform/venues/list-markets). An account stream takes `{"accountId": "…"}`.

A stream refused before it starts returns an ordinary [error response](/api-reference/platform/errors). Only `429` and `5xx` are worth retrying; anything else needs a fix.

A `200` means the subscription is live. Close the response to stop the stream.

## Read the lines

Every message has a `type`:

| `type` | Streams | Meaning |
| --- | --- | --- |
| `Reset` | Account orders, market data | The topic's whole current state. Replace everything you hold for this stream. |
| `Update` | Account orders, market data | A change to apply on top of the last `Reset`. |
| `Event` | Account transactions | One new balance posting. |
| `Ended` | All | The stream stopped. Nothing more follows. |

`Reset`, `Update` and `Event` carry `timestamp`, when Plurex sent the message, and `data`, the payload. Its shape is on each stream's page.

A **blank line** is a keepalive. One arrives as the stream opens, and again at least every 15 seconds while the stream is quiet. Skip it, but treat a stream that stays silent much longer than that as lost.

New message types and fields can be added. Ignore a `type` you do not recognise.

## Market data streams

A market data stream starts with a `Reset` holding the topic's current state, then sends `Update`s. A `Reset` can arrive again at any time and replaces everything you hold: do not merge it with your copy. How to apply each `Update` depends on the stream: see [Follow market data live](/guides/market-data#follow-market-data-live).

## Account streams

The order stream starts with a snapshot of the open orders, so it is all you need to keep them current. The transaction stream has **no snapshot**: it sends each new posting as an `Event`, and you pair it with a read of the history.

### Account orders

The order stream sends one `Reset` with the account's open orders, then an `Update` for each change to any of the account's orders. Unlike a market data stream, it sends the `Reset` only once, as its first line. Every host that supports the stream sends every change type.

```json
{"type":"Reset","timestamp":"2026-10-26T08:17:18.100Z","data":{"orders":[{"type":"Limit","id":"BTC-USDT-SPOT|5fee96c0-8063-412d-8b4d-e36e44a8ea2d","createdAt":"2026-10-26T08:17:17.709Z","side":"Buy","instrument":{"type":"Spot","base":"BTC","quote":"USDT"},"state":"Live","sizeTraded":"0","averagePrice":null,"realizedPnl":null,"totalFees":[],"clientOrderId":"my-order-1","origin":"User","size":"1","price":"90"}]}}

{"type":"Update","timestamp":"2026-10-26T08:17:18.732Z","data":{"change":{"type":"Cancelled"},"order":{"type":"Limit","id":"BTC-USDT-SPOT|5fee96c0-8063-412d-8b4d-e36e44a8ea2d","createdAt":"2026-10-26T08:17:17.709Z","side":"Buy","instrument":{"type":"Spot","base":"BTC","quote":"USDT"},"state":"Cancelled","sizeTraded":"0","averagePrice":null,"realizedPnl":null,"totalFees":[],"clientOrderId":"my-order-1","origin":"User","size":"1","price":"90"}}}
```

Each `Update` carries the `change` and the complete `order` after it, exactly as [Get an order](/api-reference/platform/hosts/get-order) returns it:

| `change.type` | Meaning |
| --- | --- |
| `Opened` | The order appeared on the stream. Each order opens once; orders in the `Reset` do not. An order first seen already traded is followed by `Filled`. |
| `Filled` | The order traded more, or reached `Filled`. The order's `state` and `sizeTraded` say whether it is partly or fully filled. The execution itself is not included: read it with [List fills](/api-reference/platform/hosts/list-fills). |
| `Cancelled` | The order was cancelled. |
| `Rejected` | The host rejected the order. `reason` and `code` are the host's own text and code, or `null`. The `code` is the host's native code, not a Plurex error code. |
| `Other` | Any other change to the order, such as an amended price or size. `nativeType` is the host's own status for it, or `null`. |

There is one `Update` per change, so a single host report that fills an order and cancels the rest sends `Filled`, then `Cancelled`, each with the same order. Intermediate states can be merged, for example several fills arriving as one `Filled`, but a final state is final: an order that reached `Filled`, `Cancelled` or `Rejected` gets no further updates.

Store the latest order you receive for each order ID, and use `change` to decide what to react to. Handle an unrecognised `change.type` as `Other`.

The stream covers every order on the account, including any the host places itself: a liquidation order opens here with `origin` set to `Liquidation`.

### Transaction events

Each transaction event is one new balance posting, with the same `id` that [List account transactions](/api-reference/platform/hosts/list-transactions) returns for it:

```json
{
  "type": "Event",
  "timestamp": "2026-10-26T08:20:00.120Z",
  "data": {
    "id": "trade-fee:7f3a",
    "effectiveAt": "2026-10-26T08:20:00.104Z",
    "amount": { "asset": "USDT", "value": "-0.055" },
    "type": "TradingFee",
    "instrument": { "type": "Perp", "base": "BTC", "quote": "USDT" },
    "orderId": "BTC-USDT-PERP|0b6c1e52-2f7e-4c55-9d43-1c1a9b6f2e10",
    "fillId": "fill-91",
    "positionId": null,
    "groupId": "trade:BTC-USDT-PERP:fill-91",
    "nativeType": "TRADE_FEE",
    "description": null
  }
}
```

Transaction events are not ordered relative to order updates, so a fee can arrive before or after the fill it belongs to. See [Balances, positions and settings](/guides/portfolio#transactions) for `amount` signs, posting types and links.

### Keep a correct local copy

**Open orders.** The order stream's `Reset` is your snapshot, so there is nothing else to read:

<Steps>
  <Step title="Replace your open orders with the Reset">
    Hold the orders from `data.orders`, keyed by `id`.
  </Step>
  <Step title="Apply each Update">
    The newest order for an ID replaces what you hold. Drop an order once its `state` is `Filled`, `Cancelled` or `Rejected`.
  </Step>
  <Step title="When the stream stops, open it again">
    Its new `Reset` replaces your copy. An order you held that is missing from it closed while no stream was open: read it with [Get an order](/api-reference/platform/hosts/get-order) if you need to know how it ended.
  </Step>
</Steps>

**Transactions.** The transaction stream does not replay postings from before it opened, so pair it with a read of the history:

<Steps>
  <Step title="Open the stream first">
    Wait for the `200`. From then on every new posting arrives as an event; keep reading and queue the events while you do the next step.
  </Step>
  <Step title="Read recent history">
    Page through [List account transactions](/api-reference/platform/hosts/list-transactions) as far back as you need, or, after a reconnect, a little past the newest posting you already hold. This is your starting copy.
  </Step>
  <Step title="Apply events on top">
    Apply the queued events, then live ones. Add any posting whose `id` you do not have.
  </Step>
  <Step title="When the stream stops, do both again">
    Postings made while no stream was open are gone from the stream. Open it again, then read history again.
  </Step>
</Steps>

Opening the stream first closes the gap: a posting made after your read also arrives as an event, and matching on `id` removes duplicates. Reading past the newest posting you hold catches one that reached the host's history late. The `listTransactions` capability's `defaultOrdering` says whether history comes newest or oldest first.

## When a stream stops

A stream stops in one of two ways.

**With `Ended`.** The last line says why, with a `code` from the [error catalogue](/api-reference/platform/errors). `message` is for logs; do not parse it.

```json
{"type":"Ended","code":"UpstreamFailure","message":"Upstream stream ended"}
```

**Without `Ended`.** The response ends or fails, the connection drops, or the stream [falls too far behind](#keep-up-with-the-stream). Messages have been lost.

Either way, open the stream again after a short, randomised delay, so that many clients do not reconnect at once, and rebuild from its first message: the new `Reset` for market data and account orders, or a fresh read of history for account transactions. Back off further if reopening keeps failing, and stop on a `4xx` other than `429`: that needs a fix, not a retry.

## Keep up with the stream

Read lines as they arrive. A stream whose client falls too far behind is cut, without an `Ended` line, rather than delaying it. Hand messages to a queue as soon as you read them, and do slow work, such as REST reads, elsewhere.

Open one stream per topic. Each stream is cut on its own, so a busy order book never delays your order updates. Over HTTP/1.1 each stream holds a connection; HTTP/2 shares one connection between all your streams.

## A resilient reader

This sketch keeps a local L2 order book for one market and the set of open orders for one account, across `Ended`, disconnects and resets. It uses [`requests`](https://requests.readthedocs.io/). Each stream runs in its own thread and only updates memory, so it keeps up with what it reads.

```python
import json, os, random, threading, time
from decimal import Decimal

import requests

API = "https://api.plurex.io/api/v1"
HEADERS = {
    "X-API-KEY": os.environ["PLUREX_API_KEY"],
    "X-API-SECRET": os.environ["PLUREX_API_SECRET"],
}
RETRYABLE = {429, 500, 502, 503, 504}
TERMINAL = {"Filled", "Cancelled", "Rejected"}

def follow(path, body, on_message):
    """Keep one stream open, calling on_message() for every line. Each reopen starts with a Reset."""
    delay = 1
    while True:
        try:
            # The read timeout is the longest silence allowed; a keepalive arrives at least every 15 s.
            with requests.request("QUERY", f"{API}/{path}", json=body, headers=HEADERS,
                                  stream=True, timeout=(10, 45)) as response:
                if response.status_code != 200:
                    error = response.json()
                    if response.status_code not in RETRYABLE:
                        raise RuntimeError(f"{response.status_code} {error['code']}: {error['message']}")
                else:
                    delay = 1
                    for line in response.iter_lines():
                        if not line:
                            continue                     # keepalive
                        message = json.loads(line)
                        if message["type"] == "Ended":
                            print("stream ended:", message["code"], message["message"])
                            break
                        on_message(message)
                    # Ended, or the body finished without it: either way, reopen.
        except (requests.ConnectionError, requests.Timeout, requests.exceptions.ChunkedEncodingError):
            pass                                         # lost: reopen
        time.sleep(delay * random.uniform(0.5, 1.5))     # randomised, so clients do not reconnect together
        delay = min(delay * 2, 60)

# L2 order book: a Reset replaces the book, an Update sets or removes levels.
book = {"bids": {}, "asks": {}}

def on_book(message):
    if message["type"] == "Reset":
        for side in ("bids", "asks"):
            book[side] = {}
    if message["type"] in ("Reset", "Update"):
        for side in ("bids", "asks"):
            for level in message["data"][side]:
                price, size = Decimal(level["price"]), Decimal(level["size"])
                if size == 0:
                    book[side].pop(price, None)
                else:
                    book[side][price] = size

# Account orders: the Reset is the open orders, each Update replaces one order.
ACCOUNT_ID = os.environ["PLUREX_ACCOUNT_ID"]
open_orders = {}

def on_orders(message):
    if message["type"] == "Reset":
        open_orders.clear()
        for order in message["data"]["orders"]:
            open_orders[order["id"]] = order
    elif message["type"] == "Update":
        order = message["data"]["order"]
        if order["state"] in TERMINAL:
            open_orders.pop(order["id"], None)
        else:
            open_orders[order["id"]] = order             # newest update wins

threading.Thread(target=follow, daemon=True, args=(
    "hosts/stream/SubscribeToAccountOrders", {"accountId": ACCOUNT_ID}, on_orders)).start()
follow("venues/stream/SubscribeToOrderBookL2s",
       {"venueId": "bybit", "instrument": {"type": "Perp", "base": "BTC", "quote": "USDT"}},
       on_book)
```

## What a stream does not promise

- No replay of missed changes on any stream.
- No sequence numbers or resume tokens. A gap shows as a fresh `Reset` on a market data stream, an `Ended`, or a stream that stops without one.
- No ordering between streams, such as between the order stream and the transaction stream.
