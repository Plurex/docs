## Requests

Commands are `POST`; queries and streams are `QUERY`. Every operation has a JSON body, `Content-Type: application/json` and both [API key headers](/authentication), and goes to a path of the form `/api/v1/{domain}/{query|command|stream}/{Action}`. IDs such as `accountId`, `hostId` and `venueId` go in the body, never in the path. See [Commands, queries and streams](/api-reference/platform/overview#commands-queries-and-streams) for the three kinds of operation.

`QUERY` ([RFC 10008](https://www.rfc-editor.org/rfc/rfc10008)) is a safe method that carries a body. Most HTTP clients send it as a custom method, in uppercase, for example `curl --request QUERY` or `requests.request("QUERY", url, json=body)` in Python.

### When you cannot send QUERY

Every query and stream also accepts `POST`. Use it when something between you and Plurex refuses `QUERY`: an HTTP client such as Java's `HttpURLConnection`, a proxy, firewall or gateway, a scripting platform with a fixed list of methods, or a client generator that drops OpenAPI 3.2 `query` operations. A `POST` to a query or stream path is the same operation, with the same body, response, permissions and errors, and it is still safe to repeat. Only the path decides what kind of operation it is.

The specification lists queries and streams under `QUERY` only, so their reference pages show `QUERY`; send the same request with `POST` instead. Commands accept only `POST`. Any other method returns `405 MethodNotAllowed`.

Every operation needs a body, even a list with no filters: send `{}` for the first page. Request bodies are strict: unknown fields, unknown enum values and wrong types return `400 InvalidRequest`. Send only the fields the specification defines.

## Responses

Successful responses use one of three shapes:

| Shape | Used for | Example |
| --- | --- | --- |
| `{ "data": ... }` | A single result, or an unpaged list such as a batch lookup | `{"data": {"id": "ord_789", ...}}` |
| `{ "items": [...], "nextCursor": ... }` | A page of a paged list | `{"items": [...], "nextCursor": null}` |
| `{}` (`Ack`) | A command with nothing to return, such as a cancel | `{}` |

An `Ack` is an empty object today; fields may be added later, so do not test it for emptiness.

Every field a response schema declares is present. Optional values are sent as an explicit `null` rather than left out, so `"averagePrice": null` means the host did not report it. Errors use the [error envelope](/api-reference/platform/errors).

## Paging

Open-ended lists are paged, and the server chooses the page size. Omit `cursor` for the first request, then pass the returned `nextCursor` as `cursor` with the same query variant, account and filters. Stop when `nextCursor` is `null`. An empty page with a `nextCursor` is not the end: a quiet stretch of history can return one, so keep going. Follow cursors on every paged list, even one that usually fits in a single page.

For example, the next request to [List accounts](/api-reference/platform/accounts/list) has this body:

```json
{
  "tenantId": "YOUR_TENANT_ID",
  "cursor": "CURSOR_FROM_PREVIOUS_RESPONSE"
}
```

Cursors are opaque. A cursor sent with a different query or account returns `400 InvalidRequest`.

Pages are read live, not from a snapshot, so items can change while you page. For host lists, the variant's capability entry gives its `defaultOrdering` (`Chronological` or `ReverseChronological`), which holds within and across pages. [Candles](/guides/market-data#candles) and [funding periods](/api-reference/platform/venues/list-funding-periods) are always newest first; candles have their own paging rules.

## Capabilities and variants

Read [venues](/api-reference/platform/venues/list), [hosts](/api-reference/platform/hosts/list) and their market summaries before choosing operations. Calling an unsupported operation or variant returns `422 NotSupported`. See [Capabilities](/capabilities/overview).

Unions use a `type` discriminator. Operations with several access patterns take them as variants in a `query` or `command` field, for example `GetOrder` with `ById`, `ByClientOrderId` or `ByClientOrderIdForInstrument`. `SubmitOrder` takes an `order` whose `type` is `Limit`, `Market`, `TriggerLimit` or `TriggerMarket`. Each variant has its own required fields and its own capability entry; all variants of one operation return the same shape.

## Batches

Batch operations take a list of identifiers, but they report missing items differently:

| Operations | Input | Missing or failed items |
| --- | --- | --- |
| [Get orders](/api-reference/platform/hosts/get-orders) | Order IDs or client order IDs | Unknown identifiers are left out of the result. |
| [Cancel orders](/api-reference/platform/hosts/cancel-orders) | Order IDs or client order IDs | One result per identifier, `Cancelled` or `Failed` with a code. The call can partly succeed; inspect every result. |

## Sizes and instruments

Instruments are always sent as structured objects, such as `{ "type": "Perp", "base": "BTC", "quote": "USDT" }`, never as symbols. See [Instruments](/concepts/instruments).

Every `size` (in orders, fills, positions, order books, trades and size rules) is in the market's **native contracts**, not necessarily base-asset units: one contract is `contractSize` units of `contractSizeAsset`, from the market's `contractDetails`. A `notional` is an amount of the quote asset.

## Decimals and timestamps

Exact decimal values, including prices, sizes, balances, rates and leverage, are **JSON strings** such as `"0.01"`. Parse them into a decimal type and keep their precision; never round-trip them through binary floating point.

| Kind | Format | Example |
| --- | --- | --- |
| Timestamps | RFC 3339 date-time | `"2026-10-25T09:30:00.250Z"` |
| Dates, such as a future's `expiry` | `YYYY-MM-DD` | `"2026-12-25"` |
| Durations, such as statistics windows and candle history limits | ISO 8601 duration | `"PT24H"`, `"PT720H"` |

## Errors and retries

An error alone never proves a command had no effect. See [Errors](/api-reference/platform/errors) for the error envelope, every code, the retry rule for each operation and how to reconcile.

## Streams

A stream operation follows one topic, such as one market's order book or one account's orders. Its `200` response stays open and carries one JSON message per line (`application/jsonl`), and every message has a `type`. Market data streams and the account order stream start with a `Reset`, then send `Update`s. The account transaction stream sends an `Event` per posting, with no snapshot. A stream stops with an `Ended` line saying why, or without one if it is cut off. Streams do not replay missed messages; see [Streams](/guides/streams) for how to read, reconnect and reconcile.

## Compatibility

Responses can gain fields, enum values, union variants and error codes without a new API version. Ignore unknown response fields, handle unknown enum values and variants as an unrecognised case instead of failing, and handle an unknown error code by its HTTP status. Removing or renaming any of them would be a breaking change. Requests must still use only the fields and values the server accepts.
